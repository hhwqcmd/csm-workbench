# AI coding 最佳实践栏目

## 定位与讲解路径

本栏目面向企业研发治理演示，不绑定具体 AI coding 产品。页面不是功能清单，而是一套可以沿着真实任务讲解的工程闭环：

> 模糊需求 → 可验收规格 → 项目知识装配 → 小任务计划 → 护栏内执行 → 证据验收 → 经验回流

页面使用“为存量订单接口增加可选优惠券字段，同时保持旧调用方、参数顺序、错误码和幂等行为不变”作为贯穿案例。讲解者可以依次切换 Specify、Context、Plan、Implement、Validate、Evolve 六个步骤，查看每一步的关键问题、工程机制、过关证据和当前产物。

四个栏目继续保留，但职责重新定义为：

1. **Agent 资产管理**：呈现执行护栏。Rules、Skills、MCP、Memory、Hooks、Plugins、Commands、Subagents 分别约束上下文、流程、权限、角色与反馈，不再按“功能是否齐全”评价。
2. **项目资产**：呈现项目理解基础设施。Wiki 服务人的阅读与导航，知识卡片服务 Agent 的任务理解，Memory 保存经验证的长期经验，启动/验证/测试入口提供可执行事实。
3. **代码质量**：呈现规格驱动的证据链。Specify、Plan、Implement、Validate 是交付主循环；AI 自检、只读 Review Agent、Agent 验收、人工审查是四层门禁。
4. **AI 效能度量**：同时观察 AI 代码进入主干的规模、资产复用、模型资源消耗与端到端交付周期。TOP 3 用于识别部门或资产差异，不作为单一绩效结论。

前三部分是产品中立的最佳实践指南，不展示虚构的资产数量、覆盖率、项目分数或 PR 结果；仅第四部分使用明确标注的模拟组织与指标。

## 最佳实践的层次逻辑

### 第一层：价值目标从代码生成转向可验证交付

代码生成只是研发链路中的一个局部环节。若需求澄清、方案评审、Review、联调、测试和返工没有被改善，即使代码生成率显著上升，整体交付周期也可能不变，甚至因为额外审查和修复而增加。

因此页面先展示三个生产问题：

1. 局部生成加速没有穿透完整交付链；
2. 存量系统存在参数顺序、下游调用、迁移窗口等隐性契约；
3. 跨模块复杂任务容易超过单次会话的稳定上下文边界。

这三类问题共同导向一个结论：AI coding 必须成为团队工程能力，而不是个人 Prompt 技巧。

### 第二层：规格是人和 Agent 之间的意图接口

规格不应是宽泛的需求描述，而应是可以驱动计划、实现和测试的“意图代码”。一份可执行规格至少包含：

- 用户故事与业务目标；
- 不允许破坏的系统约束与兼容边界；
- 可测试、无歧义的验收条件；
- 风险 Owner、人工决策点和未覆盖范围。

当需求变化时先修改规格，再调整计划、实现和测试。这样 Review 判断的不是“代码看起来是否合理”，而是“实现是否符合已经批准的意图”。

### 第三层：项目知识是任务理解基础设施

项目知识的目标不是给模型塞入更多文本，而是用合适粒度、在合适时机提供高密度工程语义：

- Wiki 面向人，存放在 `zh/content/` 一类主题目录中，按阅读逻辑组织项目概述、快速开始、核心功能、架构、配置/API 与故障排查等完整文章；目录、`<cite>` 文件引用和代码行级章节来源共同支撑阅读与核验；
- 知识卡片面向 AI 与工具，存放在 `knowledge/` 一类结构化目录中；每个代码模块固定包含概述、架构设计、技术栈、编码规范、特殊配置与命令五类卡片，并用 `_module.yaml` 与顶层 `_index.yaml` 描述 scope、模块树和依赖关系；
- Memory 保存经过验证的长期事实、偏好和复盘结论；
- 代码、Git、启动脚本和测试始终是需要现场核验的执行事实。

知识需要经历“扫描代码与文件关系 → 按模块生成五类结构化卡片 → 更新模块元数据与顶层索引 → 按主题生成 Wiki 与代码引用 → Owner 校正 → 按 scope 和依赖预取 → 当前代码核验 → 来源 Diff 触发局部重建或失效”。没有来源提交、Owner、时效和失效条件的内容不能自动进入任务上下文。

### 第四层：工程护栏把不确定生成变成受控执行

规格回答“做什么”，项目知识回答“理解什么”，工程护栏回答“如何受控执行”：

- Rules 固化目录级架构与业务底线；
- Skills 和 Commands 固化可重复的任务方法、停止条件与证据格式；
- MCP 与 Hooks 控制外部工具权限和确定性危险操作；
- Subagents 分离执行、审查和验收职责；
- Plugins 负责按团队场景打包、版本化和回滚整套能力。

所有复杂需求都应拆成可独立验证的小任务。每个任务明确输入、输出、依赖、允许路径、停止条件和验收命令；通过后及时形成稳定提交点，避免后续上下文漂移覆盖已有成果。

### 第五层：质量来自规格一致性与证据闭环

代码质量门禁按以下顺序建立：

1. 执行 Agent 把 Diff 对回 Spec 与任务清单，并运行权威验证入口；
2. 只读 Review Agent 同时读取 Spec、计划和 base SHA，沿完整调用链核对兼容性与同步变更；
3. 验收 Agent 从 Spec 生成 Given / When / Then 矩阵，逐条关联测试、截图或人工结论；
4. 模块 Owner 处理业务歧义、架构取舍、风险接受和最终合并。

任一 P0/P1 未关闭、关键验收条件无证据或未验证外部状态被隐藏，都不得声明交付完成。

### 第六层：每次任务都要让工程系统变强

任务结束后进入成功/失败双向复盘：

- 成功：把有效方法提炼为 Skill、Rule、知识卡片或回归测试；
- 可控失败：需求不清补 Spec，知识缺失补关系卡片，约束失效补 Rule/Hook/Test，结构难改先处理技术债；
- 能力边界：缩小任务、减少上下文、改为人工主导或交给专项角色，明确接管点和未验证项。

自迭代不是让 Agent 自行修改所有规则，而是由工程证据触发候选更新，再由 Owner 审查后进入团队资产。

## 最佳实践摘要

### Agent 资产管理

- Rules：绑定实际目录和风险。例如结算写链路必须透传 `idempotency_key`、禁止记录手机号和完整请求体，并指定准确验证命令。
- Skills：一个 Skill 解决一个可命名问题；表结构迁移等流程必须写清输入、回滚 Owner、停止条件、隔离验证和完成产物。
- MCP：Review Agent 只允许 `ticket.get`、`ci.get_run`、`logs.search` 等只读工具；写操作切换到需人工批准的角色，审计日志只保留元数据。
- Memory：每条长期事实包含 `source`、`verified_at`、Owner 和失效条件；版本、价格、端口和外部状态必须定期复核。
- Hooks：前置阻断只匹配高确定性危险命令；单脚本单职责、目标耗时小于 2 秒，并测试允许、阻断、解析失败和超时路径。
- Plugins：围绕单一团队场景打包，发布物料列出组件版本、权限差异、冒烟入口和回滚版本。
- Commands：要求 base SHA、模块和环境参数；固定输出变更范围、命令退出码、风险与未验证项，缺少参数时不得猜测执行。
- Subagents：审查角色默认只读，只报告本次变更新增且有证据的问题；按 P0–P3 返回位置、影响、最小修复和验证命令。

### 项目资产

- Wiki 按人的阅读主题组织完整文章，而不是按代码模块机械分组。每页包含目录、`<cite>` 文件引用以及代码行级章节来源；关系元数据单独维护父子关系、顺序与 `dependent_files`，使阅读结构与生成治理解耦。
- 知识卡片按代码模块组织，每个目录固定使用 `概述.md / 架构设计.md / 技术栈.md / 编码规范.md / 特殊配置与命令.md`；`_module.yaml` 描述 scope、来源和依赖，顶层 `_index.yaml` 固定 schema 并导出模块树。模块变化必须同步重建索引，并补齐 Owner、来源提交、复核日期和失效触发器。
- AGENTS.md 采用“根级共性底线 + 模块级局部事实”，明确脏工作树处理、安全边界、权威验证入口和外部状态声明。
- 启动脚本的 `--check` 只诊断版本、依赖和端口；不得停止未知进程、覆盖 `.env`、静默安装或调用生产接口。
- 验证入口使用 `set -euo pipefail`，按格式、静态检查、测试、构建和安全扫描顺序执行，禁止用 `|| true` 吞掉失败。
- 测试规模按关键链路管理层级和失败场景；同时记录 flaky 比例与隔离期限，而不是只展示测试总数。

### 代码质量

- 执行 Agent 先运行 `git diff --stat`、`git diff --check`，检查密钥、生成文件、锁文件和无关重构，再运行受影响模块的验证入口。
- Review Agent 对照 base SHA 阅读完整调用链；P0/P1 必须给出触发条件、影响和验证路径，纯风格意见标为 Nit。
- 验收 Agent 使用 Given / When / Then 需求矩阵，并覆盖主路径、权限失败、边界输入和回滚；真实 API 与部署状态分别声明。
- 人工 Reviewer 使用 CODEOWNERS 路由高风险目录，主分支要求必需检查和 Owner 批准；推送新提交后旧批准失效，禁止 AI 自动合并。

## 可复制模板

页面为 8 类 Agent 资产、6 类项目资产和 4 层质量门禁各提供一个默认折叠的“可复制模板”，共 18 个：

- Agent 资产：目录级 Rules、数据库迁移 Skill、MCP 权限策略、长期记忆、危险命令 Hook、能力包清单、验证 Command、只读 Review Agent。
- 项目资产：系统 Wiki、知识卡片、AGENTS.md、启动脚本、验证脚本、测试清单。
- 代码质量：PR 自检摘要、Review finding、验收矩阵、CODEOWNERS。

模板中的团队名、路径、命令和阈值是可编辑基线，复制到项目后必须按当前仓库、CI、权限模型和风险等级复核，不能直接视为生产配置已批准。

## 模拟组织与指标

页面 AI 效能度量部分中的“星河零售集团”、部门、指标、趋势和质量摘要全部为仓库内模拟数据，不对应真实客户、员工或代码仓。

核心指标：

- AI 代码行数 TOP 3：统计期内带 AI 会话溯源且进入 PR 的新增与修改代码行；排除生成目录、锁文件、第三方代码与重复快照，按部门汇总。该指标只反映使用规模。
- AI 代码入库率 TOP 3：合并至受保护主干的 AI 辅助代码行 / 提交到 PR 的 AI 辅助代码行，按部门计算。
- Skill 使用率 TOP 3：调用指定 Skill 的有效 AI 任务 / 该 Skill 适用任务，按 Skill 汇总；不以安装量代替实际使用。
- MCP 使用率 TOP 3：至少成功调用一次对应 MCP 的有效 AI 任务 / 允许使用该 MCP 的 AI 任务，按 MCP 汇总。
- Token 消耗量 TOP 3：统计期内模型输入 Token + 输出 Token，按任务归属部门汇总；缓存命中按实际计量口径计入。
- 需求交付周期 P50：需求进入规格澄清到通过全部门禁并合并的中位时长；需与返工和逃逸缺陷同时观察。

榜单名称与数值均直接呈现在卡片中；部门榜单用于识别推广、成本或转化差异，Skill/MCP 榜单用于识别高复用资产。代码量和 Token 消耗量不得独立解读为交付价值。

## 模拟 API

只读同源接口：

```text
GET /api/ai-coding/metrics
  ?org_id=org_nebula_retail
  &period=30d
  &scope=organization
```

响应固定包含 `data_mode: simulation`。五个榜单指标在 `metrics[].ranking` 中返回名称、原始值和展示值；P50 返回数值、单位和变化幅度。响应还包含组织筛选、四周趋势与代码质量摘要，响应头同时返回 `X-Data-Mode: simulation` 和 `Cache-Control: no-store`。

该接口不得扩展为任意上游代理，不接收 API Key，也不得接入员工身份、真实 Prompt、代码内容、会话记录或生产研发效能系统。
